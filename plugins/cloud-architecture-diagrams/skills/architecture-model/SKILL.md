# Architecture model

Turn an architecture request into a reviewable JSON model and check it with this plugin's command, `"${CLAUDE_PLUGIN_ROOT}/bin/cloud-diagrams"`. Run it by that quoted full path, because the plugin's `bin` folder is not reliably on the Bash path, and run it on its own with nothing chained after it, because this skill pre-approves only this command. The JSON is the source of truth: the renderer draws from it, and later edits build on it, so a correct small model beats a complete-looking guess.

## What this version can do

The `capabilities` subcommand is authoritative. At this version:

- **Implemented:** schema and catalog discovery; strict structural, identity, reference, cycle, view, Kubernetes context, catalog, provider placement and Kubernetes semantic validation; and SVG/PNG rendering of one view at a time into a checked bundle.
- **Host requirement:** rendering needs Graphviz and the macOS sandbox. `render_available` and `render.host_blockers` in `capabilities` say whether this host has them.
- **Not implemented:** PDF or DOT export and automatic overview/detail generation.

A `"valid": true` result means the model passed the core, catalog and documented provider rules (`validation_scope: core_catalog_provider`). It does not prove that anything is deployed, that traffic is reachable, that a policy is enforced or that a controller is available, and it does not render a picture; `render` does that separately. A rule fires only on what the model declares, so a missing zone or Pod placement stays unspecified. Say so whenever you report a result, because the user may otherwise treat it as architecture approval.

If `render` is unavailable or fails, say so and offer the validated model. Do not fill the gap by writing `diagrams` Python, Graphviz DOT or other generated code to execute: the project accepts architecture input as data only, and an image made outside the controlled renderer would skip its checks and approved icons.

Hand over a bundle's files as the plugin wrote them. Never edit, translate, redraw or convert `diagram.svg` or `diagram.png`, and never show a changed image in their place, even when the user asks for every label in Thai. Copying the files unchanged is fine. The model's names, labels, titles, `environment` and relationship labels are drawn as written, so write those in Thai. The renderer adds English text of its own. Any view can show provider headings, the legend's heading and line kinds, such as `traffic` and `storage`, and each node's type name. It can also show notes on what a resource or box belongs to, which start with a word such as `subnet:`, `location:`, `namespace:` or `security:` and then give the model's names, and `node: unspecified` on a Pod placed on no Node. Kubernetes detail views add property lines, such as `type: ClusterIP` and `ports: 80:8080/TCP`, and reference notes, such as `service:` and `storage class:`. The `DRAFT` lines of a lenient render and the lines on icon rights are English too. Tell the user that this text stays in English.

### Huawei Cloud icons

Huawei Cloud service icons are accepted by the owner for private personal use only. Their rights are not cleared, so any model using them returns one `ASSET_PRIVATE_USE_ONLY` warning. A rendered bundle that shows them states the same limit in its `rights` and in the image. Report it, and do not suggest publishing the output or sharing it outside private use.

If a type returns `ICON_UNAVAILABLE`, it has no usable icon, and `render` refuses it in both modes with `RENDER_TYPE_BLOCKED`. Keep its native service name, and never propose a generic symbol or an icon pack found elsewhere as a stand-in.

## Workflow

1. **Check the runtime.** Run `"${CLAUDE_PLUGIN_ROOT}/bin/cloud-diagrams" capabilities` once. The first run may download Python dependencies. Exit code 3 means the runtime could not be prepared or failed unexpectedly: relay the stderr message rather than installing packages yourself. Exit code 64 means the command was used incorrectly, so check the usage message on stderr.
2. **Understand the request.** Identify the providers and environment. Ask about uncertainty that changes the architecture's meaning, such as whether "ECS" means AWS or Huawei Cloud. Record smaller working choices in `metadata.assumptions`. Do not add resources, security controls or connectivity the user did not ask for; offer them as labeled suggestions and include them only once accepted.
3. **Look up exact types.** Run `"${CLAUDE_PLUGIN_ROOT}/bin/cloud-diagrams" catalog --provider aws --query "load balancer"` to find a `service_type`, its one `taxonomy` ID and its placement rule. Filters are `--provider`, `--entity`, `--taxonomy`, `--query`, `--type`, `--kubernetes` and `--limit`, and `--taxonomy-list` lists the taxonomy IDs. Never guess an ID. Unknown types fail in strict mode.
4. **Author the JSON.** Read [references/model-guide.md](references/model-guide.md) before writing a model, and use [examples/core-valid.json](examples/core-valid.json) or [examples/kubernetes-valid.json](examples/kubernetes-valid.json) as a shape to follow. Its `metadata` needs `id`, `title` and `environment`, a short label such as `production` or `development` that each view's title shows in brackets, so write it in the labels' language. Choose each view's `grouping` and selection from the guide's section on choosing what a view selects. Save the model with the Write tool in the user's working folder, for example `architecture/<metadata.id>.json`, and never inside this plugin's own folder.
5. **Validate.** Run `"${CLAUDE_PLUGIN_ROOT}/bin/cloud-diagrams" validate < architecture/model.json`, with the model's path relative to the working folder as shown, because an absolute path can need a separate approval. One run checks every view and lists each view's excluded IDs in `view_exclusions`; `--view <id>` only chooses which view `selected_view` and `excluded_ids` describe. The `valid` field in the JSON gives the outcome. Exit 0 means valid; exit 2 means invalid, with the diagnostics on stdout.
6. **Fix by diagnostic.** Each diagnostic gives a `code`, a `field` path and a `remedy`. Correct the model; do not delete a requested component or relationship to make validation pass. If a request cannot be expressed, tell the user. `--mode lenient` marks a draft and turns only an unknown `service_type` into a disclosed warning, keeping the provider, type and label. It bypasses no other error, so it is not a way past a failure.
7. **Render, when the user wants a picture.** Run `"${CLAUDE_PLUGIN_ROOT}/bin/cloud-diagrams" render --output architecture/rendered < architecture/model.json`, adding `--view <id>` to pick a view; the first view is the default. Each run validates again and draws one view, so run it once per view the user wants. `render` creates a missing output root itself, private to the user, so run no `mkdir` or `chmod` first. An existing root must be a real directory, with no symbolic link in its path and not writable by group or others. On macOS that rules out `/tmp` and `$TMPDIR`, whose paths hold a symbolic link, so keep the root in the project. Read the `rendered` field: only `true` means a bundle exists, and `artifacts` lists each file's path and checksum. Show `diagram.png` with the Read tool and look at it before you report: check that labels are readable and that nothing requested is missing. A loose box for a region or zone, or one long column of resources, means the view needs changing rather than the model, so adjust the view as the guide says and render again. A `RENDER_PNG_SCALED` warning means the PNG was shrunk to fit, so tell the user and point to `diagram.svg`, which keeps full size. Exit 2 means the model is invalid or the view cannot be drawn as asked, for example `RENDER_VIEW_TOO_LARGE`, `RENDER_PIXEL_LIMIT` or `RENDER_PNG_SCALE_LIMIT`, whose remedy is to split the view. The pixel limit applies to the full-size image, so it can refuse a view inside the entity limit. Exit 4 means this render failed and published nothing, so relay the diagnostic's remedy, for example installing Graphviz. In `--mode lenient` the image and manifest are marked DRAFT, and an unknown type is drawn with the approved generic symbol; never present that as a final diagram.
8. **Report.** State what was modeled, the assumptions, the validation result, any warnings and the pending checks. Tell the user every ID that `view_exclusions` lists, view by view, by its name from the model and its ID, relationships included, for example: the overview leaves out Availability Zone A (`az-a`) and Availability Zone B (`az-b`). Do not summarize, group or leave out any of them, and never put a reason, such as being shown another way, in place of naming them; give the reason after. A partial view must never silently drop a component. If you rendered, give the bundle path and relay `rights`, including any private-use limit and draft marking. Otherwise state that no image was produced.

## Editing an existing model

Change the same file and keep existing IDs, including those of unrelated resources and relationships, so diffs and future diagrams stay comparable. Tell the user what changed, then validate again.

## Data the model must not contain

Do not place secret values, credentials or real tokens anywhere in the model. A Kubernetes `Secret` resource is a reference marker with no properties; the name is fine, the payload is not.
